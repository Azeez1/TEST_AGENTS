# Visual direction

Choose a look before implementation; do not default to the same hero every time.

| Subject | Visual language | Useful visual form |
|---|---|---|
| Invisible computer processes | Precision instruments, routes, packets | A live path with labeled stages |
| Nature or living systems | Field notes, warm paper, organic silhouettes | A cutaway with a controlled change |
| Decisions and tradeoffs | Editorial comparison, strong typographic contrast | Matched before/after scenes |
| Abstract relationships | Tactile objects, containers, tokens | Objects that move or regroup |

These are starting points, not topic restrictions. Use the user's design if given.

Give the first viewport a clear question, a short orientation sentence, and a
large visual or immediately visible control. Balance dramatic display type with
plain explanatory text. Use contrast, whitespace, and a restrained accent.
A diagram should remain understandable if decoration is removed.

Bundle uses local Georgia, Trebuchet MS, and Consolas fallbacks so offline
lessons still work. Override the pair when it serves the concept. Use SVG
viewBox and readable labels; on small screens redesign the arrangement rather
than shrinking a desktop schematic until labels are illegible.

Three included token palettes:
- paper: warm ivory, almost-black ink, cobalt, tangerine;
- ink: dark navy, pale text, cool blue, warm orange;
- garden: pale green paper, forest ink, green, ochre.
Use data-theme on html or a local section. Tokens are a foundation, not a requirement.

Motion should encode a fact: a request travels, a queue grows, a boundary blocks.
Keep timings illustrative unless backed by measured data. Provide reset and
pause when a sequence runs continuously. Prefer click-driven scenes over autoplay.
Never hide the only explanation behind animation or hover.

Use layers intentionally: overview first, a nearby control second, deeper detail
third. Optional references and caveats can be smaller, but still legible.
