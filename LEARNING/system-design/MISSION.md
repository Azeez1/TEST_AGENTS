# Mission: System Design

## Why
EZ wants to reason about and design systems with authority — from first principles, not memorized templates. This one skill serves four real fronts at once: (1) passing system-design interviews (Insight-tier roles), (2) architecting his own multi-agent / Dux Machina AI systems so they scale and don't fall over, (3) advising consulting clients (CTOs/founders) on architecture trade-offs credibly, and (4) general fluency in how large systems are actually built.

## Success looks like
- Can walk up to a blank whiteboard and design a system (e.g. URL shortener, news feed, a multi-agent pipeline) out loud, justifying every component from a fundamental reason — not "best practice says so."
- Can name the specific limit (compute, memory, storage, failure, latency, consistency) that each component (load balancer, cache, replica, shard, queue) exists to solve.
- Can explain any of these to a smart beginner using a plain-English analogy (Feynman test).
- Can map classic distributed-systems patterns onto AI/agent architecture (orchestration, context, memory, cost).

## Constraints
- Starting level: some exposure — has built apps, knows the vocabulary, cannot yet design from scratch.
- Learning style (non-negotiable, from skill): First Principles for *what/order*, Feynman for *how* — plain English + analogy first, one idea per lesson, teach-back at the end.
- Prefers concise, no info-overload, one idea at a time.

## Out of scope (for now)
- Deep low-level implementation (writing a Raft library, kernel networking). We learn the *concepts and trade-offs*, not production internals — unless a lesson needs a peek to make the idea land.
- Cloud-vendor-specific certifications (AWS/Azure exam trivia). Vendor names appear only as examples of a fundamental.
